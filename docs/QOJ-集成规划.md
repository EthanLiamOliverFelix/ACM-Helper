# QOJ 集成规划

## 目标与边界

QOJ 首期作为第四个题目来源接入 ACM Helper，优先保证题目导入、本地编写运行、题单与 AI 推荐可用。远端提交放在第二阶段，并坚持由 QOJ 官方页面持有登录 Cookie；应用不读取密码、不导出 Cookie。

## 阶段一：题目与本地工作流

1. 识别 `qoj.ac/problem/<id>`、比赛题目链接及可能的镜像域名，统一保存为 `platform: "qoj"` 与站内数字题号。
2. 从题目页提取标题、时空限制、题面、输入输出、样例和来源。HTML 先转为项目统一的结构化 HTML/Markdown，公式交给现有 KaTeX 渲染链。
3. 将 QOJ 加入题库来源、题单批量输入、资源文件元数据、笔记、错题复习和 AI 候选池。
4. QOJ 没有稳定公开的全量题库接口时，不做启动时全站扫描；采用“链接导入 + 最近使用缓存 + 可选分页索引抓取”，避免给站点造成高频请求。

验收标准：导入十道不同类型 QOJ 题目时，题面、全部样例与限制完整；打开同一题复用同一本地代码文件；可加入题单并被 AI 选中。

## 阶段二：登录与人工提交

1. 使用独立、持久化的 QOJ 官方 WebView 登录窗口，并通过页面上的用户入口识别登录成功。
2. 采用与 Codeforces/AtCoder 相同的保守提交模式：点击提交后复制当前代码，打开对应题目的官方提交页，由用户粘贴并提交。
3. 返回应用后询问是否 AC；确认后写入提交记录、完成状态、技能熟练度与复习系统。
4. 登录检测和窗口打开使用 QOJ 独立 busy 状态，不得阻塞其他 OJ 的账号按钮。

验收标准：登录、切换账号、关闭窗口、超时都能恢复按钮；不同 QOJ 题目的提交页地址正确，代码完整进入剪贴板。

## 阶段三：可选的自动结果同步

仅在 QOJ 页面结构和使用规则允许时实现：

- 从当前用户的提交记录页读取本人提交的 ID、状态、耗时与内存；
- 用“题号 + 提交时间 + 语言”匹配本地人工提交记录；
- 轮询采用退避和总超时，失败时保留人工确认入口；
- 页面结构变化只影响 QOJ provider，不影响其他平台。

不计划自动绕过验证码、反机器人机制或以应用读取的 Cookie 直接调用私有接口。

## 建议的代码结构

在 Rust 侧逐步抽出统一 provider 接口：

```rust
trait OjProvider {
    async fn fetch_problem(&self, reference: &str) -> Result<Problem, OjError>;
    fn manual_submit_url(&self, problem: &Problem) -> Result<Url, OjError>;
    async fn inspect_account(&self, app: &AppHandle) -> Result<AccountStatus, OjError>;
}
```

前端把目前名称带 `cf` 的人工确认状态改为 `manualSubmissionConfirmation`，包含 `platform` 字段。`Platform`、`SkillPlanProblem`、`ProblemSetEntry`、错题复习记录和批量解析器统一增加 `qoj`，避免在各页面继续堆叠平台分支。

## 缓存与更新策略

- 题面按 `qoj:<id>` 缓存，并保存 `fetchedAt` 与解析器版本；
- “重新抓取”只刷新当前题，手动“更新题库”只刷新索引；
- 解析失败保留旧的完整缓存，不能用残缺响应覆盖；
- 诊断日志只记录状态码、页面类型和脱敏错误，不记录 Cookie、源码或登录信息。

## 风险与回退

- QOJ 页面和部署版本可能变化较快：为选择器准备 HTML fixture 测试，并在解析器中保留多套选择器。
- 部分题目包含附件或自定义交互：首期显示附件链接并标注“特殊评测”，不假装支持本地完整判题。
- 若站点明确限制自动抓取，则关闭索引同步，只保留用户主动打开链接后的单题导入。

## 推荐里程碑

- M1：链接识别、题面解析、fixture 测试、题单与 AI 支持。
- M2：官方 WebView 登录、人工提交、提交确认与错题系统联动。
- M3：可选结果同步、比赛分析、异常诊断和解析器兼容测试。
